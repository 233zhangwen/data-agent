## 1. 三个工具：先能回答「为什么需要它」

| 工具 | 不做的代价 | 可测收益 |
|---|---|---|
| `search_schema` | 逐张 `describe_table`，每张一轮 LLM 往返（2–4s） | 3–5 张表的完整列定义一次到位 |
| `make_chart` | 模型自己拼图表 JSON，参数错和渲染错分不清 | 参数错当场被拒 + 列出可用列名 |
| `save_query` | 项目缺「有副作用」的那一半 | 未确认不落库（查库可证） |

### 1.1 `search_schema` 为什么**不用**向量检索

W1 spec 里写着「21 张表就必须有 search_schema」，很容易顺势上向量（项目 #1 的 RAG 经验还在手边）。**不上**，四个理由：

1. **候选空间只有 21 篇。** 向量检索的优势是「同义不同词」，而这里 query 和文档共用同一套术语（问「复购」必然命中订阅表的文档）。小语料上，词频类方法的 precision 通常更高。
2. **表名列名是专有名词。** `orders`、`subscription_seats` 这类词字符串匹配的 precision 接近 1，向量反而会把 `invoices` 和 `payments` 混起来。
3. **确定性才能单测。** 向量要 mock embedding 才能测打分，而 mock 过的打分等于没测。
4. **少一个故障点。** demo 已经依赖 DeepSeek，再接一个 embedding 服务，线上挂一个就演示不了。

替代方案：`rankTables(query, docs)` 纯函数 —— 中文 2-gram + 英文词元，IDF 加权，返回 `{ table, score, matched[] }`。
`matched` 一起给模型**和**前端：前端能显示「因为命中『复购』『订阅』所以选了 subscriptions」。
这比一个分数更有说服力 —— **可解释的检索**。

**什么时候改成向量**：W3 评测里量 recall@3，**< 0.85 才改**。`schema_docs.embedding` 字段（vector(1024)）留着不动。
这条要写进 README —— 「本来打算用向量，量完发现不需要」比「我用了向量」更像工程判断。

### 1.2 `make_chart`：数据不经过模型的手

最直觉的做法是让模型把数据贴进参数（`{ data: [...] }`）。三个问题：数据过一遍模型会被改写（少一行、数字变字符串、四舍五入），**而且无法区分是 SQL 错还是模型抄错**。

所以：服务端在 `state.lastResult` 里记住**最近一次 `run_sql` 的结果**，`make_chart` 只传 `{ chartType, xKey, yKey, title }`。校验四件事：

| 校验 | 不通过时的返回 |
|---|---|
| `xKey`/`yKey` 在 `lastResult.columns` 里 | 报错 + **列出全部可用列名** |
| `yKey` 的值全是数字 | 报错 + 指出哪一列才是数值列 |
| `line` 图要求 `xKey` 是时间列 | 报错 + 建议改 `bar` |
| `pie` 只允许一个 `yKey` | 报错 + 说明饼图表达的是占比 |

数据由 SQL 确定性产生，模型只决定「怎么画」。**这条分工是 chart 模块能被单测的前提。**

### 1.3 `save_query`：两阶段，且确认端点**不接收 SQL**

1. `save_query({ title, sql, question })` → 服务端生成 `proposalId`（UUID），写 `query_proposals`（`consumed_at` 为 null，`expires_at = now()+10min`，`session_id` 来自 cookie），返回 `{ proposalId, title, sql }`
2. 前端渲染确认卡片（SQL 高亮 + 「确认保存」/「不要了」）
3. `POST /api/saved-queries/confirm { proposalId }` → 服务端从**库里读 SQL** → 写 `saved_queries`

三个必须钉死的点：

- **确认请求体里没有 SQL。** 否则客户端可以改了 SQL 再确认，两阶段等于零。攻击面不在「能不能绕过按钮」，在「确认接口信不信客户端」。
- **单次消费用条件更新**：`UPDATE ... WHERE id=$1 AND session_id=$2 AND consumed_at IS NULL AND expires_at > now()`，`rowCount === 1` 才继续。双击并发只有一次成功（项目 #2 W20 的原子消费）。
- **proposal 绑 session**。项目没有登录（显式不做），用 httpOnly cookie 的随机 id 做最小隔离 —— 不是为了安全，是为了「两个浏览器窗口别串」。

## 2. 死循环：三级检测，从最便宜的往上用

| 级 | 触发条件 | 动作 |
|---|---|---|
| **L1 完全重复** | 同一条 SQL（空白折叠 + 大小写归一）第二次出现 | 不执行，直接告诉模型「完全相同，结果不会变」 |
| **L2 同错重复** | 同一条错误消息（去掉 position）第 3 次出现 | 强提示「问题不在写法，在于你对 schema 的理解 → 先去 describeTable」 |
| **L3 无进展** | 连续 3 次工具结果指纹相同 | 停止，要求如实说明没查到什么 |

**为什么 L2 是重点。** W1 的观察：模型报错后会改 SQL，但改的方向是**猜**（改列名拼写、换 JOIN 顺序）。同一个错误出现 3 次，说明它猜错了维度 —— 需要的是重新看结构，不是再改一版。这条把「错误信息」转成「诊断指令」，是「自修」从碰运气变成有策略的关键。

判据：开 / 关 L2 各跑同一批注入故障，比修复成功率与平均步数。

### 3.1 C13 怎么注入故障（这周的工程核心）

「让模型自然出错」不可复现，量不出数。注入点有两处，各管一件事：

**① C13（修复率）——注入在输入侧，不碰产品代码。**
评测问题就是「用户贴来一段别人写的 SQL」：*帮我看这条 SQL 有什么问题、修好它，然后告诉我结果。*
12 条缺陷 SQL 覆盖 6 类：错误列名 ×4、类型不匹配 ×2、漏 GROUP BY ×2、缺 JOIN 条件 ×2、除零 ×1、日期比较类型错 ×1。
这不是造出来的场景——「帮分析师修一条跑不通的 SQL」本来就是真实工作流；而且**第一个错误的发生时刻是确定的**，重试次数才有资格成为指标。
对比实验：同一批 SQL 在 L2 开 / 关（`evalFlags.disableL2`）下各跑一遍，比较修复率与平均重试次数。

**② C14（死循环有界）——注入在文档层（`faults.driftColumns`）。**
`createDataAgent({ faults })` 让 describeTable 对指定表**多显示一个不存在但看起来合理的列**
（如 orders 显示 `created_at`，真名是 `ordered_at`）→ 模型照着写 → 必然报错 →
再 describe 也拿到同一个幻觉列 → 这是一个**设计上不可解的失败**，用来看 L1/L2/L3 能不能在
MAX_STEPS 之前停下来。产品路径永远不传 faults——环境变量会留在生产代码里，半年后没人记得它是干什么的。

原始设计（往 describeTable 里**藏**真实列）被推翻：藏了列模型就不知道它存在，根本不会写出那
条 SQL——得到的是"答错"，不是"报错重试"，量的是别的东西。

## 4. 实施顺序

1. **纯函数先行**：`rankTables`、`buildChartSpec` —— 不依赖 LLM，先把确定性部分钉死并写单测

4. **故障注入**：`faults` 参数 + L1/L2/L3 检测

6. **UI（只做必要件）**：确认卡片 + Recharts 渲染
7. 回归 + 记录

### 7.2 C13：判据被推倒重来一次（第五次判据误判）

第一版评测把「用户贴来一条坏 SQL，请 Agent 修好再执行」当作唯一场景，跑出**修复率 1/12 = 0.08**。

失败原因不是模型差，是**我的判据错了**：12 条里 11 条的 `sqlErrors = 0` —— 模型压根没执行坏 SQL，
它先读了一遍，静态找出 4 个 bug，改对了才执行。回答里给的是真实数字（“business 客户净营收 3339.0 万”）。
我的操作性定义要求「必须撞过一次 SQL 错误」，于是把**更好的行为**判成了失败。

重设计后拆成两条路径，分开量：

| 路径 | 提示 | 结果 |
|---|---|---|
| **A 静态审查** | 「这条 SQL 有什么问题？修好并执行」 | 交付 9/12 = 0.75，其中 **75% 全程零报错**（纯静态修复） |
| **B 报错驱动** | 「帮我执行这条 SQL」（不提示有问题） | L2 开 **10/12 = 0.83**，平均重试 0.92；L2 关 9/12 = 0.75，重试 1.00 |

**结论**：C13 的门槛 0.75 达成（0.83）。L2 诊断指令相对关掉 +8pp、平均重试 -0.08——
样本 12 条，差距在噪声边缘，**不敢说显著**，保留它的理由是它成本为零且方向为正。
B 路径的两条失败也不是"修不了"：其中 grp-1 模型选择「解释清楚但不执行」（1 步完成），属于策略选择而非能力缺陷。

**留个教训的余数**：判据的方向永远是「把对的判成错的」，五次都是。看到数字难看时先读判据，再看模型。

### 7.3 C8：0.842 → 0.917 的两处修正

第一版 20 题只有 **0.842**，差 0.008 到门槛。逐个看失败案例，两类问题：

1. **我的标注错了**：期望表集里写了 `subscription_seats`，但库里真实表叫 `subscription_seat_changes`（席位变更流水），
   "当前座位数"其实在 `subscriptions.seats` —— 判据里有个不存在的表。
2. **分析师黑话不在文档里**：「实收」在 `payments` 的文档中一个字都没有（只在 invoices 的 pitfall 里被提了一句），
   「销售额」「座位」同样。这不是算法问题，是**语料缺口**。

修法：给 8 张表加 `synonyms` 字段（真实同义词，不是为评测造词）。

**中间还翻了一次车**：给 `order_items` 写的同义词是「销量、卖出**多少**」，2-gram 切出泛化的「多少」，
凡是问句带"多少"的题全被它抢分 → 分数反而掉到 0.817。改成「销量、售出数量、成交明细」后回到 0.917。
**这是"同义词要精确到词，不能带口头语"的实证。**

剩余 3 条未满分（销售额/退货率/座位），原因都是「一道题有多条正确路径」——`orders` 和 `order_items`
都能答"品类销售额"，排名先后不是错。**期望表集对'多路径问题'过严**是这套标注的已知局限。

### 7.4 C15：thinking 关不掉（W1 遗留假设被证伪）

| 模式 | outputTokens（3 次均值） | reasoningTokens |
|---|---|---|
| disabled | 1287 | 457 |
| enabled | 640 | 80 |

方向反了——但看单次数据就明白这是**轨迹噪声**（disabled 有一次跑了多步，reasoning 1247）。
真正的问题是：**两个模式下 reasoning tokens 都不为 0**。

直接验证（`eval/probe-inject.eval.ts`）：请求体里 `"thinking":{"type":"disabled"}` **确实发出去了**，
响应仍带 `reasoning: 19`。按官方文档再试 `reasoning_effort: "none"`（文档明写它能关），**同样被忽略**。

**结论**：注入中间件没问题，是端点当前不尊重这两个参数（模型版本行为漂移——项目 #1 时这个假设是成立的）。
影响：思考 token 无法关闭，成本控制实际靠 `MAX_STEPS`。注入代码保留（端点恢复尊重时自动生效），
`agent.ts` 的注释已按实测事实改写。

### 7.5 C14 的意外发现：模型从数据通道绕开了文档幻觉

注入了真正的不可解场景：`describeTable` 显示幻觉列 `created_at` 并**藏掉真实列** `ordered_at`。
预期是它怎么改都错、被 L1/L2 拦住。实际结果：**5 步解决，L2/L3 都没触发**——
它执行了一次 `SELECT * FROM orders ...`，从**真实返回的列名**里发现了 `ordered_at`，绕过我造的"文档"。

这个发现比判据本身有价值：**任何"文档层"的幻觉都挡不住愿意读原始数据的模型**。
反过来说，`describeTable` 的可靠性不是决定性的——真正的 ground truth 是查询本身。
这也解释了为什么那份文档要写 pitfall（口径陷阱），而不是重复 DDL。
