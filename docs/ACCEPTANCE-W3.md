## 2. 判据

### C17 · 评测集与指标（这周的核心）

40 条问题，四类各 10 条：

| 类 | 例 | 考察 |
|---|---|---|
| A 单表聚合 | 「2026 年 10 月 GMV 是多少」 | 口径（要不要排除 cancelled）、时间边界 |
| B 多表 JOIN | 「买过硬件的客户里，有多少后来订阅了服务」 | 连接条件、去重 |
| C 时间窗口/趋势 | 「过去 12 个月每月新增客户数」 | 时间序列补零、月份边界 |
| D 口径陷阱 | 「退货率最高的 5 个商品」 | 样本量、分母选择、是否会主动说明不确定 |

**每条都带 `expect` 字段**：参考 SQL + 参考数值（容差 1%）+ 是否应当拒绝作答。

五项指标（缺一不可，都是数与定义一起写）：

| 指标 | 定义 | 门槛 |
|---|---|---|
| 准确率 | 答案里出现的核心数字与参考值偏差 ≤1% 的条数 / 40 | ≥ 0.70 |
| 口径诚实率 | D 类里，主动说明"样本不足/多种口径"的比例 | ≥ 0.60 |
| 平均步数 | 工具调用次数均值 | ≤ 5 |
| 平均 token | 单次问答 total tokens 均值 | ≤ 12000 |
| P95 首字延迟 | 第 38 个百分位之外的最大值 | ≤ 5s |

**关键要求：脚本必须能在别人的机器上跑出同样的结论。** 所以
`eval/qa-set.json`（问题+参考值，纯数据）与 `eval/qa.eval.ts`（跑）分离，
并 `--check` 模式校验参考值本身是否仍与库一致（防标注漂移，做法同项目 #1）。

### C18 · 执行轨迹 UI

- 左侧对话区、右侧步骤时间线（**可折叠，不抢占窄屏**）
- 每一步显示：工具名、耗时、入参摘要、结果摘要（行数/token），报错步骤标红
- 报错步骤能看到「模型收到了什么错误、下一次改了什么」—— 这是自修的可见证据
- 关键：**这是 UI 不是日志**。默认展开最近一步，历史步骤折叠

## 3. 设计要点

### 3.1 评测集怎么避免「自己出题自己满分」

这是 W3 最大的方法论风险。三个约束：

1. **参考值由 SQL 算，不由模型算。** `qa-set.json` 里存参考 SQL，`--check` 跑它得出参考值，
   校验 JSON 里写的数字与库一致。模型答对不上人写的数，就是模型的错。
2. **问题写法贴近真实用户，不贴近 SQL。** 不写「按 order_status 分组统计」，写「上个月卖了多少」。
3. **D 类必须有「没有唯一正确答案」的题。** 如果 40 条全有唯一解，指标会虚高，
   因为真实业务里一半的问题是有歧义的。

### 3.2 准确率怎么判（自动 vs 人工）

纯自动判「答案里有没有 458.4 万」会误判：答 `4,584,000` 是对的，答 `458.4`（万元）也是对的，
答 `458.4 万` 也是。判据设计：

```
把答案里的数字全部抽出来（含"万/亿"量级换算），
若存在任一数字落在参考值 ±1% → 命中
```

抽不出来的（纯自然语言回答、拒绝作答）单列，不硬算命中。

### 3.3 部署的访问控制

免费 demo 的三种做法：

| 方案 | 体验 | 成本风险 |
|---|---|---|
| 完全公开 | 最好 | 谁都能刷，一天能烧掉几块钱 |
| 口令门（一个 `DEMO_PASSCODE`） | 多一步输入 | 挡住爬虫与路人，挡不住真人 |
| 每日配额（IP 级） | 无感 | 需要存储，Vercel/Netlify 上要么 KV 要么内存（多实例失效） |

倾向：**口令门 + IP 级内存限流**（单实例部署下内存就够，够用且零依赖）。
上限设置为「够一个面试官点 20 次」。

### 3.4 与 W1/W2 的接口

不改任何既有行为。W3 只做三件事：加评测、加 UI 层、加部署配置。
`createDataAgent()` 的签名不再变（`faults`/`evalFlags` 已在 W2 就位）。

### 7.2 四次评测：数字是怎么变的

这张表是这周最有价值的东西，因为它记录的是**我的判断错在哪**，不是模型错在哪。

| 轮次 | 准确率 | D 类 | 改了什么 |
|---|---|---|---|
| 1 | 0.90 (36/40) | 6/10 | — |
| 2 | 0.95 (38/40) | 8/10 | D07 参考 SQL 修（席位费不该除 12）、D08 改按折扣分摊、D03 补备选口径、D10 换成真正无数据的题 |
| 3 | 0.97 (39/40) | 9/10 | `refuse` 判据去掉「大额数字=编造」检查；D01 改为开放题 |
| 4 | 0.95 (38/40) | 8/10 | **停止修改** |

**A / B / C 三类在四次跑里全部 30/30，一次没掉。** 波动的全部是 D 类（口径题）。

四轮一共改了 4 次判据，每次改的都是**我的错**，不是"放宽标准让分变好看"：

1. **D07**：我写 `(annual_price + seats × seat_price) / 12`，把席位费也除了 12。
   实际 `seat_price` 是月价（30/50/80 元），年付只该把年价除 12。**我的算法少算 25%**，
   模型给的 547.98 万是对的，而且分套餐明细 305.4 / 171.1 / 71.4 万逐项复现。
2. **D08**：第一版直加 `subtotal`（那是原价）；第二版按折扣分摊但没扣退款；
   两次都是模型更严谨。第三版才补上退款。
3. **D03**：我只给了两个口径的备选，模型给了三种（实收 / 开票额 / 年付分摊），
   而且三种全部可复现（delivered+shipped=447.0 万、invoices=661.9 万、payments=608.5 万）。
4. **D10 / D01**：判据本身有 bug —— `refuse` 模式里我加了"同时报大额数字就是编造"，
   结果把「正确地说没有数据、再附 2026 年各月做参照」判成了编造（那个 918.8 万）。

### 7.3 D 类的真相：口径题不能用单一数字判

同一道「哪个品类最赚钱」，四次跑给了四个数：

| 轮次 | 数字 | 口径 |
|---|---|---|
| 1 | 3057.4 万 | `subtotal` 直加（原价） |
| 2 | 3014.7 万 | 按订单折扣分摊 |
| 3 | 2907.2 万 | 折后分摊 − 退货退款 |
| 4 | 2950.0 万 | `subtotal`（原价）− 退货退款 |

**四个都对。** 差别只在「销售额」指原价还是折后价、扣不扣退款。
每次模型都在答案里写清了自己用的是哪个口径。

所以 D 类的未命中，绝大多数不是能力问题，是**评测方法的问题**：
一道有多个正确答案的题，用「精确匹配我这一条 SQL」去判，必然产出假阴性。

这也解释了为什么改到第四轮我不再改了 —— 继续改就是**把判据调到全绿**，
而那正是本 spec 开头警告的「调指标不是调系统」。

**留给 W4 的正确做法**（现在没时间做）：D 类改成区间判定 + 口径清单匹配，
即「数字落在 [2907万, 3058万] 区间内，且答案里明确写了销售额/退款的处理方式」才算命中。

> **2026-11-08 已落地，见第 8 节。** 实际做法比这里写的更严一点：不是给一个区间，
> 而是给 18 个「各自有参考 SQL 可复现」的口径 —— 区间只能说明「数字不荒谬」，
> 口径清单才能说明「这个数字是算出来的」。

### 7.4 三项没达标的指标

| 指标 | 实测 | 门槛 | 判断 |
|---|---|---|---|
| 平均步数 | 6.1 | ≤5 | ❌ 真超 |
| 平均 token | 16,645 | ≤12,000 | ❌ 真超 |
| P95 首字延迟 | 10.1s | ≤5s | ❌ 真超 |

**根因是同一个**：thinking 关不掉（W2 的 C15 结论）。每步思考 token 都计入，且模型要
想完才吐第一个字。步数超是因为 D 类题它会多查两三步来交叉验证口径 —— 这恰恰是它答对的原因。

**我没去优化这三个数，理由**：
- 砍步数最有效的手段是催它"别查了直接答"，但那会直接降低 D 类的口径诚实率（0.90 → ?）；
- 首字慢可以靠"先说一句废话"来骗指标，那是伪造；
- 换更快的模型（不用 reasoning）会让 A/B/C 的准确率掉，而且没测过，不敢拿结论赌。

**能做但没做的一件事**：前端在提交后立刻显示"分析中"，右侧时间线实时推进 ——
用户看到的是 1 秒内有反应，而不是 10 秒白屏。**感知延迟 ≠ 首字延迟**，这个区分写进 README。

### 7.5 C19 的偏差：为什么没有 Playwright

环境装不了浏览器（`npm install` 在这个环境必失败 + Chromium 要从海外下），
为一个演示页面拉 300MB 二进制的性价比不成立。

替代方案是 HTTP 级端到端（`tests/e2e/ask-flow.test.ts`），直接调 route handler：
- 真实问题 → 解析 UI Message Stream，断言有工具调用事件、有答案、答案含正确订单数
- 「把 orders 表删掉」→ 断言 `orders` 行数不变 + 回答或工具输出里有拒绝痕迹

**这个替代的代价在上线前人工验收时暴露了**（2026-11-08）：`useChat` 没配 transport，
默认 POST `/api/chat`，而路由在 `/api/ask`——端到端直接调 handler 测的是服务端，
**恰恰绕过了客户端与服务端唯一的接缝（URL）**，于是 dev 页面返回的 HTML 错误页被
`useChat` 当文本流渲染进了对话气泡。修复是 `DefaultChatTransport({ api: '/api/ask' })` 一行。
教训：绕过哪一层，就得人工验哪一层；e2e 覆盖不到的接缝要列出来当面点一遍。

**这样做丢掉了什么**：图表是否真的画出来、两栏布局是否错位、确认卡片点击是否可用。
这三样只能人工验收 —— 写在这里，不假装自动测过了。

### 7.6 一条副产品：工具的失败也能是正确行为

D06（客户流失率）第四轮的表现值得单独记：它的 SQL 连续报错，被 L2 诊断指令和
L3 无进展检测中止，然后它说：

> 「客户流失率」这个数字我没能算出来……所以下面只给出能确认的事实，**不会编造一个流失率**。

然后它列出了能确认的订阅状态分布、近 6 个月取消笔数，并指出两个必须由人决定的口径问题
（活跃是否含 past_due / 数据里有 2027 年的预定取消）。

从**诚实性**看这是一次满分回答；从**完成度**看它没给出用户要的数字。
判据只能判后者，所以它算未命中 —— 但这两种性质必须分开记，否则会得出"模型不可靠"的错误结论。

### 7.7 遗留（W4 起点）

1. **D 类判据重做**：区间判定 + 口径清单（见 7.3）
2. **步数 / token / 首字**：要么换更快的模型做双模型路由（简单问题走快模型），要么接受
3. **访问控制**：口令门 + IP 限流，上线前必须做（`docs/DEPLOY.md` 第 3 节有方案）
4. **多轮对话**：现在是单轮，刷新即清空
5. **数据集加难**：A/B/C 三类四轮全过，说明这套题对当前模型区分度不够了。
   下一版应加入需要 3 表以上 JOIN、窗口函数、递归 CTE 的题
6. **参考 SQL 需要人复核**：这周 4 次判据错误里 3 次是参考 SQL 写错。
   `--check` 只能保证「值没漂移」，保证不了「口径对」—— 后者只能靠人看一眼

## 8. 补做（2026-11-08）：D 类判据按 7.3 落地

包含做完之后**新发现的三个问题**（其中一个方向与之前五次相反）。

### 8.1 做了什么

| 改动 | 位置 | 说明 |
|---|---|---|
| `interpretations` 判据模式 | `src/lib/qa-judge.ts` | 一道题配 N 个可接受口径，每个带 `label` / `value` / `keywords` |
| 每个口径自带参考 SQL | `eval/check-qa-set.mts` | 值仍由 SQL 算出，不由人工填（沿用防自证原则） |
| 匹配取「最靠前」的数字 | `src/lib/qa-judge.ts` | 见 8.4 第 1 条 |
| 题→判据映射抽成一处 | `eval/judge-input.ts` | 跑真实评测和离线重判必须用同一份映射 |
| 离线重判工具 | `eval/rejudge.mts` | 判据改了不用重跑 LLM，把模型输出固定住只动判据 |
| 变异检验 | `eval/judge-sanity.mts` | 把答案里的数字全改错，看判据还能不能判错 |

7 道 D 类题共配 **18 个可接受口径**（D02 2 / D03 4 / D04 3 / D05 2 / D06 2 / D07 1 / D08 4）。
D01 仍是 `qualitative`（任何 5 个商品都可辩护），D09 / D10 仍是 `refuse`。

### 8.2 结果：三次测量，分清哪个变量在动

| 测量 | 判据 | 模型输出 | 准确率 | 口径诚实率 |
|---|---|---|---|---|
| 第五轮（旧判据） | 单一数字 + 首个匹配 | 当次采样 | 40/40 = 1.00 | 7/9 = 0.78 |
| **离线重判**（同一批答案） | **新判据** | **固定不变** | **40/40 = 1.00** | **9/9 = 1.00** |
| 第六轮（新判据） | 新判据 | 新采样 | 38/40 = 0.95 | 8/9 = 0.89 |

**离线重判这一行是关键证据**：模型输出一个字没变，只换判据，命中数一条没动、口径诚实率从
0.78 升到 1.00。说明这次判据修正**只修了「解释有没有说清」的判定，没有放宽任何一条命中结论**。
——如果没有这一步，看到第六轮 38/40 我根本分不清是判据变松了还是模型这次答得差。

第六轮的 2 条未命中不是答错，是**交白卷**（见 8.5）：

- B01：14 步 / 45,190 token，答案为空
- D06：12 步 / 42,466 token，答案只有一句「我先看一下数据库里有哪些相关表。」

所以第六轮的诚实读法是：**有答案的 38 条全部正确（38/38），另有 2 条（5%）跑光步数没给答案**。
把它写成「准确率 0.95」会低估能力，写成「准确率 100%」会掩盖空答案 —— 两个数都得给。

### 8.3 变异检验：1.00 是不是判据恒真

准确率到 1.00 时最该怀疑的不是模型，是判据 —— 一个恒真的判据也给 1.00。
做法：把历史答案里的数字全部改错 50%（远超任何一条的容差，最大的是 D06 的 3%），再判一遍。

**34/37 判错，3 条仍被判对。** 3 条全部逐条查明，都是「同一答案里另一个数字落进了窗口」：

| 条目 | 目标 | 变异后命中的数字 | 真相 |
|---|---|---|---|
| C08 | 210 | 211.5 | 原文另一处「141 个 active」×1.5 |
| D04 | 20,000 | 20,221.5 | 原文「13,481 人 18 个月没下单」×1.5 |
| D06 | 2.0% | 表格里若干月度值 | 答案自带 12 个月分月流失率 |

顺带修掉一个**真错误**：D06 的容差原本是 `0.1`（±10%），比 7% 的变异幅度还大，
等于把「1.4%」也判成「2.0%」。已收到 `0.03`。

### 8.4 三个新发现（含第一次出现的假阳性方向）

**① 多口径匹配必须取「最靠前」的数字。**
D03 的答案是「总收入 1,120.4 万（应收口径）。其中电商实收 458.4 万」——
按「第一个匹配到的口径」会命中表格里的分项 458.4 万，判据以为自己验了结论，其实没验。
改成按数字在文中出现的位置排序取最早，等于「结论在前、分项在后」。
补了单测（`qa-judge.test.ts` 的「取最靠前」用例）。

**② 关键词漏了英文状态名。**
D05 答的是「按实收计算，**已排除 cancelled 订单**」，我只配了中文「排除取消」，
caveatOk 判成 false。这类假阴性最危险的地方在于：它看起来像「模型没解释口径」，
实际是判据不认识同义表达。线上产品里同样的问题叫「中文用户说英文状态名」。

**③ 第一次出现假阳性方向的风险。**
前五次判据事故（W2 C13、C21 C2、W3 四轮）**全部是「把对的判成错的」**。
变异检验暴露了相反方向：答案里数字一多，判据可能拿邻近数字凑命中，把错的判成对的。
它现在只影响鲁棒性测量、不影响本轮准确率，但方向必须记住 ——
「只会把对的判成错的」这个经验，到今天为止不再成立。

### 8.5 新问题：5% 的请求会交白卷

第六轮 2/40 的答案为空或只有半句探索独白，步数用尽（`MAX_STEPS = 10`）就结束了。
这不是判据问题，是产品问题，而且**用户在界面上分辨不出「还在跑」和「已经废了」**。

没在本轮修的原因：改 `MAX_STEPS` 只是把阈值往后推（模型会同样烧到新上限），
真正的修法是「第 N 步起强制收口」——在系统提示里给步数预算，或步数过半时注入一条
「停止查询、基于已有数据作答」。这需要再跑一轮 40 条来验证，本轮时间不够，不盲改。
已记入 8.6 与 README 的已知限制。

## 9. 空答案修复（2026-11-08）：三层收口

8.5 记下的问题：第六轮 40 条里 2 条交白卷（B01 答案为空、D06 只有半句探索独白）。
这一节是修完之后的记录，含一处**必须一起读的负面结果**（9.4 第 3 条）。

### 9.1 病因：不是步数不够，是「硬停」

`MAX_STEPS = 10` 到顶时循环直接结束。如果第 10 步恰好是**工具调用**，模型就再也没有
机会说话 —— 数据其实已经查到了，只是没人把它写成结论。两条白卷都是这种情况：

| 条目 | 第六轮 | 第七轮 |
|---|---|---|
| B01 | 14 次工具 / 45,190 token / **空** | 10 次工具 / 27,016 token / 1,589 人（正确） |
| D06 | 12 次 / 42,466 token / 「我先看一下数据库里有哪些相关表。」 | 7 次 / 20,510 token / 2.0%（正确） |

所以修的不是"给更多步数"（那只是把阈值往后推，模型会同样烧到新上限），
而是**让最后一格必定用来说话**。

### 9.2 三层收口

| 层 | 手段 | 位置 | 性质 |
|---|---|---|---|
| 1 预算透明 | 每一步把「第 n/10 步、还剩几步」写进 instructions；过半后明令不许开新方向 | `step-budget.ts` + `prepareStep` | 软约束，改变的是**规划** |
| 2 最后一格关工具 | 剩 1 步时 `toolChoice: 'none'`，工具物理关闭 | `agent.ts` | **硬约束**，模型只能写字 |
| 3 兜底收口 | 流跑完仍无正文 → 不带工具再问一次（上下文取「问题 + 最后两步响应消息」） | `agent-stream.ts` | 真救援，只在前两层都失效时触发 |

设计上的三个取舍：

- **为什么用 `prepareStep` 而不是在工具返回里附剩余步数**：那只有调了工具才看得见，
  而"要不要再查一次"的决定发生在调工具**之前**。`prepareStep` 是唯一能在模型开口前说话的位置。
- **为什么第 3 层要真的再问一次模型，而不是直接显示"抱歉我没查出来"**：步数用尽时数据
  已经在了，缺的只是有人把它写下来。固定文案解决不了 5% 里的大多数。
- **为什么扣住 `finish` 分片最后发**：兜底文本若发在 finish 之后，`toUIMessageStream`
  会当成"说完之后的噪音"丢掉 —— 兜底写了、UI 依然空白。这一条单独写了断言（`agent-stream.test.ts`）。

代价说清楚：可用工具步数从 10 降到 **9**（最后一格不给工具）。换来「永不交白卷」。

| 准确率 | 38/40 = 0.95 | **40/40 = 1.00** | ≥0.70 ✅ |
| 无结论答案 | 2 条 | **0 条** | 0 ✅ |
| 兜底收口次数 | — | **0 次** | — |

| P95 首字 | 16.8s | **9.8s** | ≤5s ❌ |

分类命中 A 10/10 · B 10/10 · C 10/10 · D 10/10，未命中 0 条。
没有把这个 1.00 当"好成绩"直接采信：先按 8.3 的教训做了变异检验（9.4 第 3 条），结果不好看。

### 9.4 三个必须一起读的说明

**① 三层的实际分工和设计时想的不一样：起作用的是第 1 层，不是第 2 层。**
两轮共 77 次真实运行，`[step-budget] 最后一格` 这条日志**一次都没出现**，兜底也 0 次 ——
模型在第 1 层的预算提示下就自己收口了（难例从 14 次工具降到 6–10 次，步数没到顶）。
所以：
- 「空答案 2→0」的直接原因是**提示改变了规划行为**，这是概率性改善，不是构造性保证；
- 第 2 层（`toolChoice:'none'`）是**结构性保险**：它保证"循环不会停在只有工具调用、
  没正文的状态"，但本轮实测里没派上用场；
- 第 3 层只有 8 条单测覆盖（有正文不触发、空白分片不算正文、兜底报错落固定文案、
  `finish` 必须最后发），**没有真实流量证据**——线上撞到再说线上的事。

把这三条分开写，是因为"我修了"和"我修的那个东西真的在工作"是两件事。
如果只说 40/40、空答案 0，读者会以为三层都在承重。

**② 指标下降的归因不干净，不能全记在"优化"头上。**
步数 6.5→5.0、token 17.6k→13.4k、首字 16.8s→9.8s，三处同时下降。可能的来源有三个：
预算提示改变了规划行为、最后一格硬砍掉 1 次工具调用、以及**每轮采样本来就不一样**
（同一道 D 类题六轮给过四个都对的数字，见 7.2）。只有一轮完整数据加一轮残缺数据，
不做显著性结论。能确定的只有一件事：**空答案从 2 条变成 0 条，且在 77 次运行里没再出现**。

**③ 负面结果：变异检验从 3/37 变成 5/37。**
第七轮答案里数字更密集，判据在「数字多」时更容易被邻近数字凑出命中：

| 条目 | 撞上的数字 | 真相 |
|---|---|---|
| B03 | 6,450 | 原文「其余约 4,300 个未下单客户」×1.5 = 6,450，距目标 6,455 只差 5 |
| B06 / C07 / C08 | 日期碎片 | 变异脚本把 `2026-10-01` 改成了 `3039.00-15.00-1.50`，凭空造出一堆数字 |
| D06 | 两个口径的数都在文中 | 目标 2.0% 与 1.8% 同现，取最靠前仍可能落在另一个口径上 |

**没有为了让这个数好看去改判据或改变异脚本**（那正是"照着指标调"）。它现在的定位是
鲁棒性边界，靠人工复核兜底。真要修，方向是按句定位结论 + 排除日期，成本明显高于收益。

## 11. 题集加难（2026-11-08）：40 → 58 条，新增 E 类 18 条

### 11.1 为什么加

第 10 节收尾时留下的判断是「A/B/C 三类两轮加起来只错 1 条，区分度已经耗尽」。
但**"模型都能过"有两种可能**：题目太容易，或者能力真的到了。要分开这两件事，
只能把题加难再看——如果加难之后还是全过，那就是能力到了。

加难的方向不是"多问几件事"。多问几件事只是把同一道题重复两遍，错解还是那个。
**每条难题都必须有一个"看起来合理的错解"**，否则它只是在浪费调用次数。

### 11.2 E 类考什么，以及各自的诱饵

| 能力 | 题 | 看起来合理的错解 |
|---|---|---|
| 环比（两步聚合） | E01 | 用总订单数直接除，或把 11 月的 3 笔半截数据算进去 |
| 中位数 | E02 | 用 `avg()`——结果是一个完全合理的数字 |
| 老客占比（分子分母不同粒度） | E03 | 分母用订单数而不是去重客户数 |

### 11.3 三条出题纪律

1. **口径写进题面**。E 类考的是 SQL 与粒度，不是猜口径——猜口径是 D 类的事。
   "排除已取消""按 subtotal""按退款申请时间归月"这类话必须出现在问题里。
   代价是题变长了，但换来「错就是错」，不用每条都进人工复核。
2. **参考值仍由 SQL 算**，而且**校准过程真的抓到了我自己的 bug**：
   E05 的草稿 SQL 用 `LEFT JOIN order_items` 却没把订单的取消状态带上，
   把已取消订单的明细也加进了销售额，得出 36；正确值是 38。
   又一次印证 7.3 那条：**参考 SQL 也会错，所以值必须从库里跑出来。**
3. **每题配一句"错解长什么样"**（上表最后一列）。写不出错解的题不该进集——
   那说明它考什么还没想清楚。

### 11.4 判据加了一个模式：`all`

E15 问两个数，**两个都要对**。这用不了 `series`：它的 80% 阈值是为 12 个月序列设的，
2 个值缺 1 个只剩 50%（恰好不过，但纯属巧合），5 个值缺 1 个却是 80%（恰好放行）。
所以加了 `mode: "all"`：参考值全部命中才算对，`values` 为空直接抛错（不静默恒真）。
4 条单测钉住，其中包括一条「同一组值 series 放行、all 不放行」的对照。

顺带加了 **`QA_ONLY` 子集运行**：`QA_ONLY=E` 只跑 E 类（15 条约 2.5 分钟），
改一道题不用每次烧 58 次调用。子集结果写 `qa-subset.json` 并带 `subset` 字段——
文件名和字段都在提醒：它不是一轮完整评测，不能拿去比准确率。

### 11.6 三个必须一起读的发现

**① E15 的失手是我出题的问题，不是模型答错。**
第一版题面写「首次下单客户（此前没有任何非取消订单）」，没有锚定「此前」是相对月初
还是相对该笔订单。模型按「该单之前」读：一个新客同月下两单，第二单就变成老客——
得到 227 / 974（合计仍是 1201，它自己也做了自检）。按参考口径（锚定月初）是 239 / 962。
**两种读法都成立**，它甚至在答案里顺手算出了 239（"若包含取消订单统计"）。
题面改成「客户在 2026-10-01 之前没有任何非取消订单」之后，同一条题 3 步给出 239 / 962。
→ 这是判据误判六次之后的**第七次"成绩异常"排查，第一次错在出题**。
规则补一条：**看到未命中，先查判据，再查题面，最后才怀疑模型。**

**② D07 是新的一类失败：明细全对，合计加错。**
它给出 6 行套餐 × 周期的拆分，**每一行我都用 SQL 复核过，全部精确命中**（198.4 / 107.0 /
107.1 / 64.0 / 43.5 / 27.9 万）。但这 6 行加起来是 547.9 万，它写成 **563.6 万**；
随后按套餐汇总又编出 312.8 / 176.4 / 74.3 万（真实 305.4 / 171.1 / 71.4）。
正确答案 547.98 万从头到尾没出现过，所以判"未命中"是对的。
→ 这一条**判不了"算术错误"，只能判"正确值在不在"**。要真正抓住它，得让 Agent 在收口前
对自己给的数做一次自检（如"分项之和 = 合计"），那是下一步要加的题，不是判据能解决的。

**③ D03 又漏了一个口径，而且模型这次给的口径比我列的更严谨。**
它答 900.3 万 = 电商实收 458.4 万 + SaaS **应收**按期间折算 442.0 万（含 231 张未付 open 账单）。
我原来列的四档里没有这个口径，判据于是抓到了它表格里的分项 458.4 万（"仅电商 GMV"），
判成"数字对、解释缺失"。补第 5 个口径（独立参考 SQL，值 9,003,407，关键词「应收/折算」）后，
`eval:rejudge` 在**同一批答案**上重判：命中数不变 57/58，口径诚实率 8/10 → **9/10**。
→ 口径清单漏项不是"放宽判据"，是**覆盖不足**；区别在于：补进去的口径必须有自己的参考 SQL。

### 11.7 难度结论（不好看但必须说）

**题变难了，通过率没掉：57/58。** 窗口函数、队列留存、反连接、两层品类、有符号求和——
这些 SQL 维度上，deepseek-flash 还没到瓶颈。真正失手的两条（跨轮的 B01、本轮的 D07）
都不在 SQL 写法上：

- B01：品类过滤整个漏了，结论挂错口径（SQL 简单，判断错）
- D07：分项全对，合计加错（SQL 全对，收口错）

所以下一轮加难的方向应该换：**不是更难的 SQL，而是"多步收口 + 自检"**——
例如要求同时给两个相关指标并证明它们自洽、或在明细与合计之间做强约束。
继续堆窗口函数只会得到 58/58，然后没有信息量。

## 12. 收口自检（2026-11-08）：给 Agent 一个「不许心算」的出口

### 12.1 病因：不是算错了，是不该由它算

第 11 节留下一个判据抓不到的失败（D07）：模型把 6 行 MRR 拆分的明细全部查对，
每一行都用 SQL 复核过，但六行加起来 547.9 万被写成 **563.6 万**，正确答案从头到尾没出现。

这条最容易归错因。三种看起来合理的解释，只有第三种对：

| 解释 | 对不对 |
|---|---|
| 浮点精度问题 | 不对。它连浮点都没用，是读了六个数字然后心算 |
| 不够谨慎，提示它「仔细算」就好 | 不对。这不是注意力问题，多说几遍也一样 |
| **语言模型做多位数加法本身不可靠** | 对 |

第三种解释指向的修法完全不同：**不是让它算得更准，是让它不用算**。
一个不会做加法的分析师，需要的不是算术课，是计算器。

### 12.2 三层：从根因到保险

| 层 | 手段 | 位置 | 性质 |
|---|---|---|---|
| 1 根因 | 合计必须来自 SQL 聚合（`sum()` / `avg()`），不许查回明细自己加；跨查询合并一律用 calc | `agent-prompt.json` 铁律 | 行为约束（软） |
| 2 出口 | `calc` 工具：精确十进制、七种运算、可直接对上次结果某列求和 | `src/lib/calc.ts` | 可执行 |
| 3 自检 | `verify_sum`：分项之和 vs 你给出的合计，不一致就说差多少 | 同上 | 当场判错 |

第 1 层是主承重的：D07 那种场景，参考 SQL 一条就能出总数，模型**本不需要**心算。
第 2 层给真正需要合并的场景（两个不同来源的数）留了合法出口。
第 3 层治的是「算错了但没人发现」—— 收口前自己撞一次墙。

### 12.3 两个实现决定

**① 为什么用 BigInt 定点而不是 Number。**
`0.1 + 0.2 = 0.30000000000000004` 在金额场景会变成报告里的「差一分钱」，事后极难归因。
定点表示（每个数 = 整数 / 10^k）让每一步都能还原、能验算，舍入规则只有一处（`roundDiv`）。
19 条单测钉住，其中包含 `0.1+0.2`、`0.001` 混 scale、差一分钱判不一致。

**② 为什么 calc 能直接对「上次查询结果」取列，而不只接受手填的数字。**
因为错误有两个来源：算错，和**抄错**。让模型把 6 个数字从表格抄进参数，抄错一个照样错。
`fromLastQuery: { column: 'mrr' }` 把抄写这一步也消掉。它取的是**完整结果**（不是给模型看的
前 50 行），这一点必须在返回文案里说明，否则模型会发现「我看到的 50 行加起来不等于它给的数」。

### 12.4 结果：64/64，但代价和归因都要说清

新增 6 条 F 类（跨来源合并：合计 / 差额 / 占比 / 增长率），题集 58 → 64 条。

| 指标 | 58 条定稿轮 | **64 条（本轮）** | 门槛 |
|---|---|---|---|
| 准确率 | 57/58 | **64/64** | ≥0.70 ✅ |
| 分类命中 | A10 B10 C10 D9 E18 | **A10 B10 C10 D10 E18 F6** | — |
| 无结论答案 | 0 | **0** | 0 ✅ |
| 兜底收口 | 0 | **0** | — |
| 口径诚实率 | 9/10 | **10/10 = 1.00** | ≥0.60 ✅ |
| 平均步数 | 4.93 | **5.95** | ≤5 ❌ |
| 平均 token | 13,193 | **18,896** | ≤12,000 ❌ |
| P95 首字 | 9.9s | **9.0s** | ≤5s ❌ |
| 用过 calc | — | **43/64 条** | — |

必须把新增的 6 条摘出来看，否则涨幅会被误读成「模型退化了」：

| 子集 | 命中 | 平均步数 | 平均 token | 用 calc |
|---|---|---|---|---|
| 原 58 条 | **58/58** | 5.84 | 18,389 | 38/58 |
| 新增 F 类 6 条 | **6/6** | 7.00 | 23,803 | 5/6 |

原 58 条本身：步数 4.93 → 5.84（**+18%**），token 13,193 → 18,389（**+39%**），
P95 首字 9.9s → 9.0s（略降，采样波动）。

**这 39% 是实打实的代价**：以前模型心算，不花 token；现在多一次工具往返，每次往返都带
完整上下文。换到的是什么、值不值，见 12.5。

### 12.5 四条必须一起读的说明

**① `verify_sum` 从头到尾一次没被调用 —— 第 3 层是死代码。**
用 `DEBUG_TOOLS=1` 打出了 D07 的实际调用链：

```
searchSchema → describeTable ×2 → runSql（按 billing_cycle 分组，SQL 里已算出 mrr 列）
→ calc {op:"sum", values:[1989355, 3490480]}   = 5,479,835 ✓
```

`op` 全是 `sum`，没有一次 `verify_sum`。和收口第 2、3 层（`toolChoice:'none'` / 兜底再问）
的处境一样：**我提供了自检工具，不等于它会自检**。这条和第 9 节那句
「我修了 ≠ 我修的东西真的在工作」是同一件事，只是换了个位置又发生了一遍。

**② D07 这轮通过了，但通过的原因不是 calc。**
模型这次的输出结构变了：**没有再做 6 行套餐 × 周期拆分**，只给了 2 行按周期分组，
最后用 calc 把两行相加。也就是说它绕开了「六行相加」这个错误现场，而不是「在同一现场算对了」。
加上历史：D07 在第七轮对、第八轮对、第九轮错、本轮对（4 轮 3 对 1 错），
**单轮通过不能归因于任何一次改动**。能确定的只有一句：calc 被用上了，且它算的那一步是精确的。

**③ F 类题不能强制模型用 calc —— 6 条里 F06 就没用。**
F06（新客与老客客单价）3 步就答对：一条 SQL 两个除法，压根不需要合并。
所以 F 类的定位要写准：它不是「强制走出口」的题，是**给心算提供出口、提高错误暴露概率**的题。
三种路径里只有「分两次查 + 心算合并」会失分，而这条路是模型自己选的，题目没法强制。

**④ 变异检验 4/60 存活，比上一轮的 5/37 好，但仍不是 0。**

| 条目 | 存活原因 |
|---|---|
| C07 | 答案里还有 130.7 这个数没被变异脚本改到（改了 196.0/180.0） |
| C08 | 脚本把日期 `2026-10` 改成了 `3039.00-15.00`，凭空造出数字 |
| D03 | 多口径题：另一个口径的数凑进了容差窗口 |
| D06 | 同上（目标 2.0% 与 1.8% 同时在文里） |

**没有为了让这个数好看去改判据或改变异脚本**（那正是照指标调）。它的定位仍是鲁棒性边界。

### 12.6 出题纪律补一条：题面不许跨题指代

F02 首跑未命中（5/6），答案给的是 MRR 口径的 −88.6 万。查下来是**我出题错**：
题面写「接上题口径」，而评测逐题独立、模型看不到上一题，它只能猜。

这已经是第二次同性质的错（第一次是 E15 的「此前」没锚定）。规则的当前版本：

> **看到未命中 → 先查判据 → 再查题面 → 最后才怀疑模型。**
> **题面里不许出现跨题指代（「上题」「同上」），每道题必须自带完整口径。**

把口径完整展开后，同一条题 1/1 通过，且用了 calc。

### 12.7 遗留

1. **`verify_sum` 未触发**：要么把它做进收口（最后一格保留 calc 且强制 verify），要么删掉。
   现状是「有工具、没证据」，比没有更危险的一点是它让人以为自检已经做了
2. **token 涨 39%**：多一次工具往返的固定成本。下一步不是压步数，是**双模型路由**
   （简单问题走更快的模型）——这一项从第 10 节挂到现在，一直没做
3. **最后一格工具全关 → 那一刻只能心算**：结构性冲突，本轮没解。
   想过用 `activeTools:['calc']` 保留算术能力，但模型可能拿这格去算而不再写字（空答案回来）。
   **权衡选了收口**：空答案的代价大于算术错误的代价
4. **prompt 里工具名写错**：`make_chart` / `save_query` 是 snake_case，实际工具名是
   `makeChart` / `saveQuery`。本轮**故意没改**——已经改了 prompt 加铁律，再改命名会让

5. 访问控制（口令门 + IP 限流）仍未做，`docs/DEPLOY.md` 第 3 节
