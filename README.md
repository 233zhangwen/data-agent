# 数据问答 Agent（Text-to-SQL）

用中文问业务数据，Agent 自己决定看哪张表、写什么 SQL、错了怎么改 —— 每一步都摊开给你看。

> 项目 #3。前两个项目分别证明「能做 RAG 并验证它」和「能做产品化」，
> 这个项目要证明第三件事：**能让 LLM 可靠地执行有副作用的操作**。
>
> 状态：W1–W3 完成（6 个工具 · 三级死循环防护 · 写操作两阶段确认 · 三层收口 · 40 条标注评测 · 两栏执行轨迹）。
> **尚未公网部署**（Netlify 免费额度 11/26 恢复），配置与清单已就绪：`docs/DEPLOY.md`。

---

## 它解决什么

给 LLM 一个数据库账号让它随便查，是最容易做的技术演示，也是最容易出事的产品。

这个项目的重点不是"能生成 SQL"，而是**出错时会发生什么**：

| 风险 | 这里的做法 |
|---|---|
| 模型删库 | 数据库账号**没有写权限** + 事务强制只读。不靠 prompt 劝阻 |
| 模型写错 SQL | 报错原样喂回去让它自己改（带 position 与 hint）；同一个错误撞 3 次就**换诊断方向**（去 describeTable），不是继续猜 |
| 模型绕圈烧 token | 三级检测：同一条 SQL 第二次不执行 / 同错第 3 次给诊断指令 / 连续 3 次相同结果直接叫停 |
| 一条 SQL 拖垮库 | `statement_timeout` 10 秒 + 返回行数硬上限 |
| 模型编数字 | 工具返回真实行数；prompt 要求"查不到就说明"，且答案必须来自执行结果 |
| 大面积扫表烧 token | 表结构只给一句话说明，按需 `describeTable`；表多时先 `searchSchema` 检索 |
| 写操作被误触发 | 两阶段确认：模型只能**提案**，确认端点只收 id、SQL 从库里读，客户端改不了要保存什么 |

## 架构

```
用户问题
   ↓
ToolLoopAgent（AI SDK 7，最多 10 步）
   ├─ listTables      → 21 张表的用途 + 当前行数（现查，不写死）
   ├─ searchSchema    → 关键词 + IDF 检索相关表，返回命中词（可解释）
   ├─ describeTable   → information_schema 现查列定义
   ├─ runSql          → 只读执行器（事务级 READ ONLY）→ 结果记在 state 里
   ├─ makeChart       → 用 state 里的结果生成图表配置（数据不经过模型的手）
   └─ saveQuery       → 生成待确认提案（写 query_proposals，不直接落库）
                          ↓
                    只读账号 data_agent_ro（只有 21 张业务表的 SELECT）
```

**两条数据库通道，互不越界**：

| 通道 | 账号 | 用途 |
|---|---|---|
| `DATABASE_URL` | 读写 | 应用状态（保存的查询、表结构索引） |
| `AGENT_DATABASE_URL` | **只读** | Agent 执行 SQL |

Agent 的能力边界和应用的写入能力是两条独立通道 —— 混在一起就说不清"谁能写什么"。

## 演示数据

21 张表、约 13 万行，一家「卖硬件 + 卖订阅服务」的公司：

- 共用维度：`customers` `regions` `channels` `employees`
- 电商线：`orders` `order_items` `products` `product_variants` `inventory` `shipments` `returns` `coupons` …
- SaaS 线：`plans` `subscriptions` `invoices` `payments` …
- 服务：`support_tickets`

数据是**脚本生成的，固定种子可复现**，且刻意做出真实结构：双 11 有峰（905 万）、
春节有谷（214 万）、复购率 59%、买过硬件的客户中 33% 后来订阅了服务（跨线分析的基础）。

> 为什么自己造而不是下载公开数据集：国内网络不可控，且真实数据集的列名常是 `col_a`、
> `col_b`，Agent 表现会被数据质量拖累 —— 那就不是在测 SQL 能力了。

## 快速开始

```bash
npm install

# 1. 建表（21 张业务表 + 2 张应用表）
npx prisma generate
# 迁移见 prisma/migrations/，用 prisma migrate deploy 或手工执行 SQL

# 2. 灌演示数据（约 13 万行，固定种子）
npm run seed

# 3. 建只读角色（安全模型第 1 层，会把连接串写回 .env.local）
node --experimental-transform-types scripts/setup-ro-role.mts

# 4. 起来
npm run dev
```

环境变量见 `.env.example`。**`AGENT_DATABASE_URL` 必须是只读账号**，
填成和 `DATABASE_URL` 一样就等于把安全交给 prompt 自觉。

冒烟测试（不打开浏览器，直接看执行轨迹）：

```bash
node --experimental-transform-types scripts/smoke-ask.mts "上个月 GMV 是多少？"
```

## 测试与评测

```bash
npm test          # 77 条单测：检索打分、图表校验、死循环检测、步数预算、收口兜底、判据本身（纯函数，秒级）
npm run test:db   # 14 条数据库/HTTP 测试：两阶段确认的原子消费与五条拒绝路径
npm run test:e2e  # 2 条 HTTP 级端到端：真实问答 + 「要求删表」后数据完好（约 35 秒）

npm run eval:check     # 校验 40 条评测集的参考值是否与库一致（防标注漂移）
npm run eval:qa        # C17：40 条标注评测 + 五项指标（约 8 分钟，40 次真实 LLM）
npm run eval:recall    # C8：20 题检索召回（纯计算，不花钱）
npm run eval:repair    # C13/C14：36 轮真实 LLM
npm run eval:thinking  # C15：thinking 开关的 token 对比

# 判据自身的两个检验（纯离线，不调模型）
npm run eval:rejudge   # 拿历史答案用当前判据重判：把「判据变了」和「模型答得不一样」分开
npm run eval:sanity    # 变异检验：把答案里的数字全改错 50%，判据还判得对吗
npm run eval:empty     # 空答案回归：两条历史白卷题，验证三层收口是否生效（约 1 分钟）
```

评测脚本在 `eval/`，跑完落 `eval/results/*.json`。**它们不是"跑绿就完"的测试**——
评估的产出是数字和失败原因，不是 pass/fail。当前结论：

| 指标 | 数字 | 门槛 | 状态 |
|---|---|---|---|
| 40 条问答准确率 | **40/40**（第七轮，见 `docs/ACCEPTANCE-W3.md` 第 9 节） | ≥0.70 | ✅ |
| 空答案 | **0 条**（第六轮是 2 条；两轮共 77 次运行没再出现） | 0 | ✅ 见「已知限制」 |
| 口径诚实率（D 类 9 条） | **0.89 ~ 1.00**（三轮） | ≥0.60 | ✅ |
| 平均步数 | 5.0（4.98） | ≤5 | ✅ 踩线 |
| 平均 token | 13,369 | ≤12,000 | ❌ |
| P95 首字延迟 | 9.8s | ≤5s | ❌ |
| 检索召回 recall@3（20 题） | **0.917** | ≥0.85 | ✅ 所以不引入向量检索 |
| SQL 修复率（12 条注入故障） | **0.83** | ≥0.75 | ✅ 同批 75% 执行前就静态修好 |
| 死循环有界 | 5 步停止（上限 10） | — | ✅ |
| thinking 关闭 | **关不掉** | — | ❌ 见「已知限制」 |

步数/ token / 首字这三项一直是同一个根因：**deepseek-flash 的 thinking 关不掉**（`docs/ACCEPTANCE-W2.md` 7.4
有注入证据）。第七轮加了步数预算与"最后一格只作答"后，三项都往下走（6.5→5.0 步、17.6k→13.4k token、
16.8s→9.8s），但**只有一轮数据、采样也不同**，不做显著性结论，见 `ACCEPTANCE-W3.md` 9.4 ②。思考 token 全计入，且模型想完才吐第一个字，步数则是因为 D 类题它会多查两步
交叉验证口径 —— 而这恰恰是它答对口径题的原因。**没有去"优化"这三个数**：催它别查会直接
降低口径诚实率，先说一句废话能骗过首字指标但那叫伪造。

### 一次完整的评测长什么样

`docs/ACCEPTANCE-W3.md` 7.2 记录了这套评测集跑了四轮的过程：
每一轮未命中的条目都人工复核，**四次修改全部是因为参考 SQL 或判据写错了，不是因为分数不好看**。

其中最有说服力的一条：同一道「哪个品类最赚钱」，四次跑给了 3057.4 / 3014.7 / 2907.2 / 2950.0 万
四个数，全部可复现、口径都在答案里写明了。**四个都对** —— 这说明 D 类（口径题）不能用
单一数字判命中，问题在评测方法而不在模型。这个结论比一个 100% 的准确率有用得多。

判据改完之后（`docs/ACCEPTANCE-W3.md` 第 8 节）：D 类不再用一个数字判，改成 **18 个可接受口径**，
每条口径都自带参考 SQL。配套两个离线工具——`eval:rejudge` 把模型输出固定住只动判据
（这样才分得清是判据变了还是模型答得不一样），`eval:sanity` 把答案里的数字全改错
看判据还判不判得错（准确率 1.00 的时候，最该怀疑的是判据恒真）。

顺带说清一件事：`eval:sanity` 抓到 3 条「改错了还判对」，全部查明是同一答案里**另一个**数字
落进了容差窗口。前五次判据事故都是「把对的判成错的」（假阴性），这是**第一次出现假阳性方向**——
判据在「答案里数字很多」时会变差，靠人工复核兜底。

第七轮换了目标：不调判据，修第六轮暴露的 2 条空答案。做法是三层收口（每步告知预算 →
最后一格关掉工具 → 仍无正文则不带工具再问一次）。结果 40/40、空答案 0，但同一次变异检验
变成 **5/37**（上一轮 3/37）——1.00 一旦出现，第一件事永远是查判据，而不是庆祝。
两条都写进 `docs/ACCEPTANCE-W3.md` 第 9 节，包括「兜底层本轮触发 0 次，只有单测没有线上证据」。

## 安全模型的四层

| 层 | 手段 | 性质 |
|---|---|---|
| 1 | 数据库账号只读（逐表 GRANT SELECT） | **权限层，绕不过** |
| 2 | 事务强制 `READ ONLY` | 引擎层，即使账号配错也拦得住 |
| 3 | `statement_timeout` + 行数上限 + 多语句拦截 | 资源层 |
| 4 | prompt 规则 | 语言层，**不作为安全依赖** |

第 1、2 层各自独立验证过（见 [`docs/ACCEPTANCE-W1.md`](docs/ACCEPTANCE-W1.md) 第 8.3 节）：
即使刻意关掉只读事务，账号权限仍然拒绝 `DELETE` / `TRUNCATE` / `DROP`。

第 4 层只管"让它少犯错"，不管"保证不出事"。这个分工写在这里，是为了防止
将来有人往 prompt 里加几条规则就以为加固了安全。

## 已知限制（写清楚，不粉饰）

- **thinking 关不掉。** `thinking:{type:'disabled'}` 与 `reasoning_effort:'none'` 都注入了请求体
  （`eval/probe-inject.eval.ts` 验证过），但 deepseek-flash 端点照常返回 reasoning tokens。
  项目 #1 时这条经验成立，现在不成立了——**经验会过期，所以关键假设要定期重验**。
  现状：成本控制靠 `MAX_STEPS`，不靠关思考。
- **`make_chart` 只画最近一次查询。** 想看两条不同查询的对比，得先把它们 JOIN 成一条 SQL。
  这是刻意的：数据只从 SQL 出，不从模型手里出。
- **`search_schema` 的关键词表要人养。** 20 题里仍有 3 题不满分，原因是"一道题有多条正确路径"
  与同义词覆盖不足。达到不达标门槛才考虑上向量检索（`schema_docs.embedding` 字段已留）。
- **没有对话历史。** 单轮问答，刷新即清空。右侧时间线也只显示最近一轮的步骤。
- **首字延迟 10–17 秒**（P95，三轮实测 10.1s / 16.8s / 9.8s），因为 thinking 关不掉。感知上不难受（提交后立刻显示"分析中"、
  右侧时间线实时推进），但**感知延迟 ≠ 首字延迟**，别把它当成性能好。
- **空答案曾经是 5%，现在两轮 77 次运行没再出现，但只有第 1 层真的在承重。** 修法不是调大 `MAX_STEPS`
  （那只是把阈值往后推），而是三层收口：每步告知预算 → 最后一格 `toolChoice:'none'` 关掉工具 →
  流结束仍无正文则不带工具再问一次（`src/lib/step-budget.ts`、`agent-stream.ts`）。
  第七轮 40 条空答案 0，**但 77 次运行里第 2 层（关工具）和第 3 层（兜底收口）一次都没触发**——
  真正起作用的是第 1 层预算提示（模型自己提前收口了）。第 2、3 层是保险：第 2 层保证
  "循环不会停在只有工具调用没正文的状态"，第 3 层只有单测覆盖、没有真实流量证据。
  代价：可用工具步数 10 → 9。
- **D 类的判据有了边界。** 已经不是单一数字判命中（18 个口径各带参考 SQL，见
  `docs/ACCEPTANCE-W3.md` 第 8 节），但数字匹配分不清「结论」和「表格分项」：
  答案里数字一多，邻近数字可能凑出命中（变异检验里 3/37 如此）。这是**假阳性方向**的风险，
  前五次判据事故全是假阴性——两个方向都出现过了。
- **渲染层没有自动化测试。** 图表是否画出来、两栏是否错位、确认卡片能不能点——只能人工看。
  端到端只覆盖到 HTTP 层（`tests/e2e/`），因为这套环境装不了浏览器。
- **`save_query` 只存 SQL 文本**，不是可执行的定时任务；保存的查询不会自动重跑。
